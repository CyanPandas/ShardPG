验收结果
修复后两轮完整真实 psql 会话回归均为 PASS_ALL_REQUESTED_FUNCTIONAL_CHECKS：
acceptance/business-r4-result.json
acceptance/business-confirmation-result.json
每轮 8 项均通过：
1. 四位客户位于四个不同分片，插入后可读。
2. 每位客户一个订单，UPDATE 后余额均为 1000。
3. 跨 worker、跨 customer/orders 的事务 COMMIT，其他会话读到完整结果。
4. ROLLBACK 撤销两个分片的金额更新及订单删除，事务内能读取自身修改。
5. REPEATABLE READ 下无脏读，其他事务提交后原快照不变，无幻读；新快照看到提交。
6. 写写冲突返回 SQLSTATE 40001；失败事务在另一个分片上先前的 +200 同时回滚。
7. DELETE 提交后可见，并成功重新 INSERT，最终仍为四位客户和四个订单。
8. 四节点 pg_prepared_xacts、DTX pending、协调登记、分支登记全部为 0。
原生身份围栏验收 PASS_NATIVE_IDENTITY_FENCE：错误身份被拒，正确 TSO 身份
幂等应用同一已提交判决；clog 的状态、start_ts、commit_ts 前后不变。
SQL 状态机回归 3/3 通过，包括：服务不可达保留登记、已有 COMMIT 不允许被回收、
待补时间戳的 COMMIT 保留、参与者未确认时保留、活跃分支不推定回滚、确认后回收。
这些 SQL 用例对 RPC/Raft 使用显式替身；上面的四节点业务验收使用真实原生引擎。

发现并解决的问题
A. 本次部署 socket 路径与 fa23 硬编码 /tmp 不符。
   在专用容器内配置 unix_socket_directories='/work/data, /tmp'，权限 0700。
   第一次 ALTER SYSTEM 将目录列表整体引用成单路径，导致启动失败；已修正，日志保留。
B. 客户端 ROLLBACK 没有进入协调提交驱动，留下 OPEN 协调登记。
   后台仅在所有已登记分支都报告顶层中止时，通过当前分片主节点的既有共识决议门
   请求 ABORT；该门拒绝覆盖 COMMIT。所有节点确认收尾后才回收登记和路由。
C. 同一 gxid 的多个本地 PREPARE 合并后，旧快照和单个分支的回调能提前注销整笔登记。
   OPEN/合并与 CLOSE/删除通过专用 LWLock 串行；注销时检查当前完整并集的持久化
   终局，任何分片仍未决都保留登记；补齐 shardpg_fc 原生 prepared 的保护检查。
D. in-doubt 闭合用物理日志的 node/local-xid 标识校验 TSO 槽位，正确判决被拒绝。
   分开传递日志头身份和 DTX 身份；DTX 身份必须精确匹配当前槽位后才能使用，保留
   分片 xid 回收围栏；日志标记继续使用原始物理日志头身份。
第一次更新复现的旧事务：TSO 4137，日志头 gxid 281474976722514，分片 xid 4108。
原先四次 INSERT 的成功应答和首次读取失败均保留；没有盲目重复插入或删表重建。
失败只读探针 4097 的路由在核对四节点均无关联事务后单独回收，SQL、08006 与
回收依据保存在 retired-readonly-probe-route.json；没有凭超时猜测业务事务结局。

验证边界与剩余风险
本轮结论限于上述小数据集、真实并发会话和 REPEATABLE READ 的功能正确性。
没有做 TPC-C 性能测试、长时间压力测试、网络分区/宕机的系统故障注入，
没有验收 SERIALIZABLE、SAVEPOINT 或客户/订单与其他七张本地表混合写入的原子性。
不把重启和选主过程中保留下来的数据读回等同于完整高可用验收。
本轮新增 journal 串行保护的吞吐影响尚未测量。第一分支登记失败等更广的故障路径
未做系统覆盖，不能由这组用例推导所有恢复路径均正确。
其他七张本地表保持空表；customer/orders 及四位客户、四个订单保留供继续操作。
